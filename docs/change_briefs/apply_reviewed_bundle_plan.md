# Change Brief: Apply the exact reviewed Databricks bundle plan

## Problem

The manual deployment workflow already ran an authenticated plan job before each
apply job, but the apply command recalculated the deployment from current
workspace state. A successful same-run plan therefore acted as review evidence
without becoming the exact input to `bundle deploy`.

The direct Databricks bundle engine supports replaying a JSON plan created by
`databricks bundle plan --output json`. The repository now captures that file,
but an apply still needs a fail-closed artifact-verification and replay boundary.

## Outcome

For development and production apply jobs:

1. Download the target-specific plan artifact created by the same workflow run.
2. Verify its exact GitHub run, attempt, commit, ref, repository, target, OIDC
   status, identity evidence, file inventory, JSON shape, byte counts, and
   SHA-256 digests.
3. Perform a fresh apply-principal identity preflight.
4. Invoke `databricks bundle deploy --plan <exact bundle-plan.json>`.
5. Continue with separately governed grants, optional immutable upload,
   optional workflow execution, and saved-query publication.

The apply job can no longer reach `bundle deploy` when the plan artifact is
missing, substituted, malformed, stale, from another target or workflow run, or
contains an unsuccessful identity/validation/plan state.

## Artifact identity

The plan job uploads:

```text
databricks-<target>-plan-<commit-sha>-<workflow-attempt>
```

The apply job downloads that exact artifact name from its current workflow run.
The verifier then checks the artifact's internal provenance against:

```text
GITHUB_REPOSITORY
GITHUB_REF
GITHUB_SHA
GITHUB_RUN_ID
GITHUB_RUN_ATTEMPT
selected target
```

Artifact naming is therefore not the sole security boundary.

## Verification contract

`scripts/verify_bundle_plan_artifact.py` accepts only regular files from this
bounded inventory:

```text
evidence.json
summary.md
bundle-validate.txt
bundle-plan.json
bundle-validate-warnings.txt  # optional and metadata-bound
bundle-plan-warnings.txt      # optional and metadata-bound
```

It verifies:

- evidence schema version 2;
- successful `plan` mode for the expected target;
- exact repository, protected-main ref, commit, run, and attempt;
- `github-oidc` authentication and well-formed identity fingerprints;
- successful validation and plan stages;
- exact filenames, sizes, and SHA-256 hashes;
- JSON-object shape for the plan;
- exact warning-file metadata when warnings exist;
- absence of symlinks, nested directories, and unexpected files.

The verifier performs no network request and invokes no Databricks command.
Failure output is one stable category and never includes plan content,
identifiers, tokens, or provider diagnostics.

## Approval and identity boundary

The `dev` or `prod` GitHub environment approval still occurs before the apply
job starts. The plan was generated by the corresponding plan identity; the
apply job independently authenticates as its configured apply identity before
replaying the plan.

Replaying the exact plan does not make mutable external state transactional. The
Databricks CLI may reject a stale plan, and a failed apply may still leave
partial provider changes. Environment approval, exact-plan replay, current
identity verification, and post-apply reconciliation remain distinct controls.

## Compatibility boundary

This capability depends on the direct bundle deployment engine and the CLI range
pinned in `databricks.yml`. A target previously managed by the Terraform engine
may require a separately reviewed deployment-state migration before its first
direct-engine apply.

## Non-goals

This increment does not:

- generate or approve a real plan;
- deploy to development or production;
- migrate existing bundle deployment state;
- upload data;
- run a workflow;
- execute SQL or mutate permissions;
- prove workspace least privilege;
- activate alerts, retention, or schedules.

## Rollback

Source rollback restores plan recomputation during deploy and is therefore a
security regression. Prefer a forward repair. If rollback is unavoidable,
disable apply-enabled workflow use until an equivalent reviewed-plan binding is
restored.

## Validation

Repository validation covers:

- exact same-run artifact naming and download;
- immutable `download-artifact` action pinning;
- artifact verification before CLI installation and deploy;
- `--plan` use for both target deploy commands;
- no unplanned direct deploy command;
- provenance, hash, shape, warning, symlink, and unexpected-file rejection;
- preservation of explicit apply input, environment approval, OIDC identity
  checks, and optional runtime controls.
